# 输入输出示例

以下为缩短后的演示，用来说明 Skill 的整理原则，而不是规定唯一输出模板。

## 输入

```text
我们进入开发以后呢，PRD原则上就不要老改了。你今天想到一个功能，明天又想到一个功能，前端后端都得跟着改，对吧？所以进入开发前要封板。那是不是绝对不能改？也不是。如果影响很小，跟技术负责人沟通清楚，可以改；影响大的，先放到下一版本。

现在 AI coding 让开发成本低很多。以前一个 MAD 版本——这里应该是 MVP——可能要几个月，现在几个小时或者几天就能验证。所以别一开始追求一百分，先做六七十分的可验证版本。上线也不是目的，上线以后要看有没有用户用、会不会回来。

好，刚才有同学问了个别的问题，我们下课再说。这个地方我再重复一遍，PRD 进入开发前要封板。
```

## 输出

```markdown
# AI 产品开发：PRD 封板与快速验证

## 内容主线

进入开发前应冻结 PRD，避免需求频繁变化扩大返工成本；AI Coding 降低了验证成本，因此首个版本应以验证用户价值为目标，而不是追求一次性完美。

## 一、进入开发前冻结 PRD

产品进入开发后，新增或改变功能会牵动前端、后端等多个环节。因此，团队应在开发开始前完成 PRD 封板，稳定当前版本范围。

封板并不代表任何内容都不能调整：

- 影响较小的修改：与技术负责人评估并沟通清楚后，可以纳入当前版本。
- 影响较大的修改：放入后续版本规划，避免打断当前开发。

## 二、AI Coding 改变了产品验证节奏

转写稿中的“MAD”结合语境应为“MVP”。传统 MVP 可能需要数月，AI Coding 则可能把验证周期缩短到几小时或几天。开发目标因此从“一开始做到 100 分”转向“先完成 60～70 分的可验证版本”。

推导过程是：开发成本下降 → 可以更快推出版本 → 更早接触真实用户 → 用真实反馈判断方向是否成立。

## 三、上线只是验证的开始

上线本身不是最终目标。上线后需要观察是否有用户使用，以及用户是否愿意再次回来，由此判断产品是否真正创造价值。

## 复习与面试表达

- 核心原则：当前版本在进入开发前封板，小改动评估后处理，大改动进入下一版本。
- 面试表达：AI 产品的首版目标不是一次性做到完美，而是用最低可行成本验证核心用户价值，再依据真实行为迭代。
```

## 整理动作说明

- 保留了原始顺序：PRD 封板 → AI 开发提速 → 上线验证。
- 合并了重复出现的“PRD 进入开发前要封板”。
- 删除了“下课再说”等课堂管理内容。
- 依据明确语境把“MAD”修正为“MVP”，并在结果中说明。
- 保留了规则的例外、推导链和可用于面试的表达。
